# Burrow 精简自建 IdP 设计

日期：2026-09-24

状态：用户已确认规格并授权实现。本文保留设计约束；实际实现结构与验证结果见开发文档及测试记录。

## 1. 目标与范围

Burrow 是面向单组织的自建身份提供方，独立实现，参考 Casdoor 的用户、应用、身份源与授权模型，不 Fork Casdoor。一次登录后，用户可以访问获授权的多个 APP。

第一版包括：

- 本地账号密码登录和预先关联的外部 OIDC 身份登录。
- 向下游 APP 提供 OIDC Authorization Code + PKCE（S256）。
- 用户组、用户、角色、权限、APP、Provider 管理。
- 首页数据看板与当前用户可登录的 APP 门户。
- 简体中文、英文；浅色、深色、跟随系统主题。
- PostgreSQL 生产存储、SQLite 本地开发支持。
- 本地开发文档与根目录单文件 Docker Compose 部署配置。

不包含：多租户、公开注册、自动创建外部用户、邮件邀请/找回、社交 OAuth 专用适配、SAML、LDAP、SCIM、MFA、Refresh Token、Implicit/Hybrid/密码授权/Client Credentials、动态客户端注册、跨 APP 同步退出、APP 内部业务权限、嵌套组、角色继承、策略脚本、独立审计分析平台。

不引入 Redis、消息队列或其他新增中间件。首版单应用副本，不支持高可用多副本。

## 2. 已确认的技术决策

| 层次 | 选择 | 职责 |
| --- | --- | --- |
| 后端 | Go + Chi | HTTP、管理 API、模块化单体 |
| OIDC | zitadel/oidc/v3 | 下游 OP 与上游 RP 协议适配 |
| 数据访问 | GORM | PostgreSQL、SQLite 数据访问 |
| 迁移 | 显式版本化迁移 | 不以生产启动时 AutoMigrate 代替迁移 |
| 前端 | React + TypeScript + Vite + Ant Design | 登录、门户、管理页面 |
| 前端工具 | Bun | 依赖、开发、构建 |
| 授权 | 固定 RBAC | 用户/组获得角色，角色获得权限 |

使用 zitadel/oidc 是为了复用协议层，并非部署完整 ZITADEL。库提供的额外授权模式必须关闭，Discovery 只能声明实际支持的能力。业务模块不直接依赖库内部类型，通过协议适配层接入。

考虑过基础库组合：标准库 HTTP/crypto、JOSE、golang.org/x/oauth2、coreos/go-oidc。后两者主要解决客户端能力，不能直接提供 IdP 服务端；自建服务端会增加协议兼容性和安全维护工作。用户确认保留 zitadel/oidc/v3。尚未进行依赖体积或性能对比，不以“运行更轻”作为已验证结论。

Go、Bun 与依赖的具体补丁版本在实施计划中核实并固定；提交 Go 模块校验文件与 Bun 锁文件。

## 3. 架构与模块边界

生产由一个 Go 进程托管前端构建产物、管理 API 和 OIDC 端点，同域提供服务。开发使用 Go 服务与 Bun/Vite 开发服务器，通过开发代理访问后端。

| 模块 | 职责与依赖 |
| --- | --- |
| 身份 | 管理用户、密码、组、外部身份关联；依赖存储 |
| 授权 | 合并直接角色与组角色，判断后台权限和 APP 访问资格；依赖身份与角色数据 |
| 会话 | 创建、校验、撤销统一会话，记录认证来源与时间；依赖身份、存储 |
| APP | 管理客户端、地址、登录方式；依赖授权与存储 |
| Provider | 管理上游配置、发起/完成外部认证；依赖 OIDC RP、外部身份关联 |
| OIDC OP | 协议请求与响应、授权码和令牌；调用会话、APP、授权服务 |
| 管理 API | 输入校验、鉴权、业务调用、稳定错误码；不重复实现授权规则 |
| 首页与记录 | 权限过滤后的 APP 列表、登录统计、基础操作记录 |

所有管理 API 在服务端校验会话、用户状态及对应权限。OIDC 授权与授权码兑换均重新校验用户、APP、访问权限及认证来源是否仍被允许。

## 4. 数据模型

使用不可变内部 ID；下游 sub 使用稳定用户 ID，不使用可变用户名或邮箱。

| 实体 | 核心内容 |
| --- | --- |
| User | 用户名、姓名、邮箱、状态、本地登录开关、密码哈希、强制改密、语言、主题 |
| Group / GroupMember | 组及用户成员关系，不嵌套 |
| Role | 角色名称、说明、内置标记 |
| Permission | 后台操作权限或某 APP 的登录权限 |
| UserRole / GroupRole / RolePermission | 显式多对多授权关系 |
| Application | 客户端 ID/类型、密钥哈希、名称、图标、状态、登录入口、回调与退出回调白名单、本地登录开关 |
| ApplicationProvider | APP 允许的上游 Provider |
| Provider | 名称、不可随意变更的 issuer、客户端 ID、加密客户端密钥、启用状态 |
| ExternalIdentity | Provider、issuer、外部 sub、本地用户 ID |
| Session | 会话凭据哈希、用户、认证方式/Provider、认证时间、过期时间、撤销状态 |
| AuthorizationTransaction | 下游请求及上游登录事务、state/nonce/PKCE 绑定、有效期和消费状态 |
| AuthorizationCode / TokenRecord | 库存储接口需要的授权码/令牌元数据及失效状态 |
| SigningKey | kid、公钥、加密私钥、启用/退役状态 |
| Event | 登录和管理事件、操作者、对象、结果、时间、请求标识 |

关联表具有唯一约束与外键。外部身份组合 (Provider, issuer, sub) 唯一，不能同时关联不同用户。不因邮箱相同而关联或合并账号。Provider 已有关联身份后不允许直接修改 issuer；更换身份源需新建 Provider 并重新关联。

授权码消费必须原子化，事务与并发测试同时覆盖 PostgreSQL、SQLite。数据库存储协议状态，不能使用示例库的内存存储作为正式实现。

## 5. 权限规则与管理保护

权限来源为用户直接角色与所在组角色的并集。默认拒绝，无显式拒绝规则。用户组用于批量授权，角色没有继承关系。

后台权限由系统内置，按模块提供查看与管理操作；授权变更属于独立的敏感管理权限。APP 创建时自动创建对应登录权限。权限页面支持查看和关联角色，不支持用户自定义表达式。

APP 内部业务权限由 APP 自行管理，Burrow 不下发后台管理权限作为业务 claims。

内置管理员角色拥有全部后台权限和 APP 访问权，但不能绕过用户/APP 禁用状态、客户端校验或登录方式限制。内置角色不能删除或改写。普通角色的权限分配不能隐式获得管理员身份；分配/撤销内置管理员角色仅限现有内置管理员。持有授权管理权限意味着可以管理普通角色授权，这是显式受信任能力。

禁止通过禁用、删除、撤销直接/组角色等操作移除最后一位有效管理员；检查与变更在事务中完成。初始化管理员具备直接内置管理员角色和本地登录能力，保留至少一位可本地登录的有效管理员以应对外部 Provider 不可用。

已有引用的用户组、角色和 Provider，先解除关联再删除。用户和 APP 日常下线优先禁用，记录保留；删除用户/APP 时事务性撤销会话/未完成授权并清理授权关联，事件不级联删除。

## 6. 登录与协议行为

### 6.1 下游 APP 登录

1. 用户访问 APP，APP 创建自己的 state、nonce、PKCE，并发起授权请求。
2. Burrow 校验 client_id、客户端状态、精确匹配的 redirect_uri、请求模式、scope 和 PKCE。
3. 无有效统一会话时，显示 APP 允许的本地登录和 Provider。先校验 APP，不能根据任意请求参数显示未授权的身份源。
4. 用户完成认证后，检查用户状态、角色权限、APP 状态和认证来源；全部满足才产生授权码。
5. APP 兑换授权码。检查客户端认证、请求绑定、PKCE、过期/消费状态，并再次检查访问资格；原子消费后签发令牌。
6. APP 验证 ID Token，建立自己的应用会话。

统一会话只复用身份认证，不复用过时的授权结果。若会话来源不在 APP 允许范围内，要求重新认证；不能静默忽略 APP 对 Provider 的限制。Provider 禁用后，该来源会话不能继续取得新授权。

首页 APP 卡片链接至已配置的 APP 登录入口，由 APP 发起 OIDC；不在门户 URL 中拼接令牌。APP 列表根据用户状态与 APP 登录权限过滤，登录方式不匹配时进入重新认证。

### 6.2 上游 Provider 登录

Burrow 作为 RP 保存独立登录事务，绑定浏览器、目标 APP、state、nonce 和 PKCE。回调校验事务、令牌签名、issuer、audience、有效期及 nonce，再按 ExternalIdentity 查找本地账号。未关联、禁用账号或不允许的 Provider 一律失败。上游认证成功不等于获得下游 APP 权限。

外部资料不自动覆盖本地授权或管理员属性。未配置可信邮件验证流程时，不宣称本地邮箱已验证。

### 6.3 支持范围与默认值

- 提供 Discovery、JWKS、Authorization、Token、UserInfo、RP-Initiated Logout。
- 仅 code flow，所有客户端要求 PKCE S256。
- 服务端 Web 客户端使用 client_secret_basic；公共 SPA 使用 none，不配置伪客户端密钥。
- scope 为 openid/profile/email；返回值受 scope 限制，稳定 sub 标识本地用户。
- 无 Refresh Token，不宣告 offline_access；需要续期时重新发起授权。
- 支持 code flow 必需的参数与错误语义；prompt=none 不得弹出交互，无法无交互完成时返回相应错误；prompt=login/max_age 触发需要的重新认证。
- 仅支持预配置回调地址，禁止通配符；SPA 令牌端点跨域访问只允许配置的来源。

以下为便于实施的初始默认值，纳入本次整体审阅：授权码 60 秒、未完成登录事务 10 分钟、Access/ID Token 5 分钟、统一会话绝对有效期 8 小时，无永久记住登录。时间可通过服务配置调整，不新增复杂管理页面。签名采用 RS256 和 kid/JWKS。

Access Token 第一版用于 Burrow UserInfo，不把它作为任意业务 API 的通用凭据。控制台使用服务器会话，而非在浏览器持久保存管理 JWT。

### 6.4 退出与失效

退出 Burrow 撤销统一会话，校验退出请求和退出回调白名单；不保证同步注销所有 APP 自身会话。撤销会话、禁用用户后，停止新的授权和授权码兑换。UserInfo 根据数据库中的令牌状态、关联会话和当前用户状态拒绝已失效访问。

已签发 ID Token 的离线签名有效性不会因数据库变更立即消失，APP 已建立的会话也不会自动消失；这由令牌有效期与 APP 会话策略控制。README 接入说明必须明确该边界。

## 7. 页面与交互

| 菜单 | 功能 |
| --- | --- |
| 首页 | 有看板权限者查看用户数、APP 数、近期登录成功/失败；全部用户查看自己的 APP |
| 用户组 | 列表、创建/编辑/删除、成员与角色维护 |
| 用户 | 创建、编辑、禁用、本地密码重置、组与角色分配、外部关联、撤销会话 |
| 角色 | 普通角色维护、权限分配、关联用户/组查看 |
| 权限 | 内置权限与 APP 权限列表及角色关联 |
| APP | 客户端、名称/图标、URL、登录方式、访问角色、密钥重置 |
| Providers | 上游配置、状态、关联 APP、密钥替换 |
| 个人设置 | 姓名、语言、主题、本地密码修改 |

菜单隐藏与按钮禁用只辅助交互，不代替后端鉴权。列表提供分页、搜索和必要状态筛选。后台不提供策略编辑器、复杂自定义页面或独立审计分析菜单。

本地账号由管理员创建临时密码，首次登录必须改密，完成前不能获得 APP 授权或后台管理能力；仅外部登录账号无需设置本地密码。重置密码撤销已有统一会话。非初始化流程不使用固定默认密码。

登录、错误页和全部业务页面支持中英文、三种主题。登录前选择保存在浏览器；登录后使用用户偏好。后端返回错误码，前端负责翻译；协议错误保持标准格式。

## 8. 安全、错误与运维基础

- 密码使用 Argon2id 等成熟密码哈希实现；下游客户端密钥仅存验证哈希、创建/重置时展示一次。
- 上游客户端密钥与签名私钥需要可恢复使用，使用经过认证的加密保存，主密钥通过部署 Secret/环境配置提供，不能进入仓库。
- 签名密钥持久化并支持运维命令轮换；旧公钥保留至其签发令牌全部过期并覆盖时钟容差，不能每次启动重新生成。
- 会话 Cookie 在生产使用 Secure、HttpOnly、SameSite；变更状态的会话 API 使用 CSRF 防护。登录成功轮换会话凭据，数据库只保存凭据哈希。
- 单实例内存限流覆盖密码登录、外部登录入口与令牌端点；重启会清空短时限流状态。未来多副本需另行设计，不宣称当前全局限流。
- 无效客户端/回调地址直接在本站报错，不能重定向到不可信地址。凭据错误不泄露账号存在性。
- Provider 网络访问设置超时与重定向限制；内网 IdP 通过显式配置允许，避免配置探测变成任意内网访问工具。
- 日志不包含密码、完整令牌、授权码或密钥。事件记录登录结果、敏感管理操作、操作者与对象，首页统计来自事件数据。
- 单进程定时清理过期协议状态和记录；初始事件保留期建议 90 天，可配置。
- 数据库不可用时认证/授权失败关闭，不退回未鉴权逻辑。提供存活和就绪探针，就绪检查涵盖数据库与迁移版本。
- 数据库备份必须配套备份/保管主密钥，否则无法恢复加密配置；文档说明恢复与密钥轮换步骤。

### 9.1 本地开发与 README

根 README 记录固定工具版本、Bun 安装依赖、环境配置、SQLite 默认启动、切换 PostgreSQL、迁移命令、一次性管理员初始化、前后端分别启动、测试与构建。给出两 APP 联调方法与退出限制。管理员初始化通过显式运维命令完成，不在公开 HTTP 端点开放首次抢注。

### 9.2 Docker Compose

根目录配置定义 app、一次性 migrate 服务、可选择启用的 PostgreSQL 服务及持久卷。app 与 migrate 使用同一镜像版本；支持本地显式构建，也支持生产拉取固定标签或 digest 的镜像。两种方式都能连接外部 PostgreSQL；本地无容器模式保留 SQLite。

README 从仓库根目录给出完整命令：本地构建、选择启用内置数据库、接入外部数据库、迁移、管理员初始化、启动、升级及数据备份。默认读取 `.env`，需要环境隔离时显式指定 `--env-file` 与 `--project-name`；不增加环境覆盖 YAML。不同环境不共用数据库、卷、公开 issuer 或密钥。

migrate 有界重试等待数据库，应用只在迁移成功后运行；初始化管理员是独立显式操作。迁移可重复执行并使用数据库锁防并发，升级采用向后兼容的增量迁移。应用启动只检查 schema 状态，镜像回滚不自动回滚数据库。

生产数据库不暴露公共宿主机端口。公开 issuer 与浏览器可访问域名一致，不使用容器内部主机名；生产通过现有 HTTPS 入口接入，说明信任代理与转发头配置。真实环境文件、数据库文件和密钥不提交仓库。

## 10. 验收与验证策略

1. 本地密码及预关联上游身份均能登录；未关联身份拒绝，相同邮箱不能串号。
2. Web 与 SPA 两个示例客户端完成 code + PKCE；统一会话可复用，APP 限制的认证来源仍受检查。
3. 用户/组角色并集正确，默认拒绝；直接调用管理 API 不能绕过权限；防止移除最后管理员。
4. 授权与兑换时均检查用户/APP 状态和权限；授权后、兑换前撤销权限也必须失败。
5. 非法回调、错误 PKCE、授权码重放及并发兑换、上游 state/nonce 错误、过期会话均被拒绝。
6. 退出与会话撤销符合已明确的边界；prompt=none、重新认证和未完成首次改密的行为有测试。
7. Discovery 声明与实际能力一致，JWKS/签名轮换可验证；用独立 OIDC 客户端联调，不能只靠同一库自测。采用适用的 OIDC 一致性测试，不宣称正式认证。
8. PostgreSQL、SQLite 均覆盖迁移、唯一约束、授权码原子消费与主要用户/权限流程。
9. 前端覆盖登录、用户/组/角色授权、APP/Provider 配置、中英文与三种主题；普通用户不显示管理能力。
10. 根目录 docker-compose.yaml 通过配置检查、本地构建/固定镜像启动、内置/外部数据库接入、迁移和重启冒烟验证；环境隔离通过环境变量和 Compose project 实现。
11. 重启后会话与密钥按持久化设计工作；日志和部署样例不存在真实凭据。
